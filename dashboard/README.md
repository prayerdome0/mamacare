# MAMA CARE — Supervisor Dashboard (Next.js)

Runs in two modes:

- **Demo mode** (default, no credentials): deterministic generated data so the
  UI is fully explorable — `npm run dev` and sign in with anything.
- **Live mode**: set `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_ANON_KEY`
  in `.env.local` (or Vercel env vars). Queries run through the anon key, so
  **RLS scopes everything to the signed-in user's facility/district**.

## Commands

```bash
npm install
npm run dev      # http://localhost:3000 (dev server)
npm run build    # static production build → ./out
npm start        # serves ./out on http://localhost:3000 (same files Vercel serves)
```

The dashboard is **100% client-side** — every page is a client component and
Supabase is queried from the browser — so `next build` exports plain static
HTML/CSS/JS into `out/` (`output: "export"` in `next.config.mjs`). There is no
server rendering, no route handler and no middleware, which is why the app can
be served from any static host and built from any directory.

## Deploy to Vercel

Two setups work. **A** is the conventional one; **B** needs no console changes
at all and is what the repository configures by default.

### A. Root Directory = `dashboard` (Next.js preset)

1. Import this repository and set **Root Directory** to `dashboard`
   (Vercel *does* read it from the project's Git settings, not from code).
2. Framework preset: **Next.js** (auto-detected once the Root Directory is
   `dashboard`).
3. Add env vars `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   (optional — without them the dashboard runs in demo mode).
4. Deploy. Vercel detects the static export and serves `dashboard/out`.

### B. Root Directory = repository root (no console changes)

Leave Root Directory empty/`.` — the root `vercel.json` handles everything:

```json
{
  "framework": null,
  "installCommand": "cd dashboard && npm ci",
  "buildCommand": "cd dashboard && npm run build",
  "outputDirectory": "dashboard/out",
  "cleanUrls": true
}
```

- `framework: null` forces the **Other** preset, so Vercel never tries to run
  the Next.js builder at the repository root (that mismatch is exactly what
  produced both `No Next.js version detected` and the raw `404: NOT_FOUND`).
- `cleanUrls` maps the exported `dashboard.html` → `/dashboard`, etc., so the
  extensionless in-app links resolve.

To reproduce the production build locally (identical files):

```bash
cd dashboard && npm ci && npm run build && npm start
```

## Troubleshooting

### `404: NOT_FOUND` / `Code: NOT_FOUND` with an ID like `cpt1::6hlvg-…`

That page is generated by Vercel's edge, **not** by this app — it means the
request never reached a deployment containing the dashboard, so no route (not
even the branded 404 in `app/not-found.tsx`) could match. Causes, in order of
likelihood:

1. **The project is building from the repository root without the root
   `vercel.json`.** Then there is no `package.json`/Next app where Vercel is
   looking and the deployment contains nothing to serve. Keep `vercel.json`
   committed, or set Root Directory to `dashboard` (setup A).
2. **You are looking at an old/other URL.** Open the project's *Production*
   domain (Vercel → Project → **Domains**) rather than a per-deployment URL
   (`…-<hash>-…vercel.app`) or a stale tab — those point at one specific
   deployment and can be protected or outdated. Hard-refresh or use a private
   window first: an old 404 is served from cache surprisingly often.
3. **The latest deployment failed or was never promoted.** Check
   Vercel → Deployments: the newest *Production* deployment must be `Ready`.
   If it is `Error`, open its build log — see the next section. Redeploy
   (⋮ → **Redeploy**, untick *Use existing Build Cache*) after fixing it.

### `No Next.js version detected…`

Vercel is running the Next.js builder in a directory that has no Next.js app
(the repository root). Fix by either committing the root `vercel.json` above,
or setting Root Directory to `dashboard` with framework preset **Next.js**.

A healthy deploy's build log ends with a route table listing `/`,
`/dashboard`, `/mothers`, `/alerts`, `/reports`.

### "Protected Deployment" / Vercel login wall for visitors

Project setting, not code: Vercel → Project → **Settings → Deployment
Protection → Vercel Authentication**. Set it to **Standard Protection** (which
keeps preview deployments private but leaves **Production** public) or disable
it. With "All Deployments" every visitor, including on the production domain,
is asked to log in to Vercel.

### A single route 404s (branded page, no Vercel error ID)

That is a normal app-level 404 rendering `app/not-found.tsx`. The dashboard's
only routes are `/` (sign-in), `/dashboard`, `/mothers`, `/alerts`, `/reports`.

## PII policy

- Aggregate views never show personal identifiers.
- Phone numbers are masked in every list view.
- CSV export is aggregate-only unless the supervisor explicitly opts in;
  even then phones stay masked. Live mode writes audit entries for exports.
